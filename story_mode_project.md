# Story Mode — Архитектурный паспорт и техническая документация

**Story Mode** — иммерсивная интерактивная новелла в Telegram с гибридным пайплайном: автоматизированный сценарный пролог (Глава 1) и монетизируемый живой диалог в реальном времени с актрисой через специализированный веб-терминал (Глава 2).

---

## 1. Бизнес-модель и концепция

* **Формат:** Интерактивное сюжетное расследование с элементами романтического триллера от лица героини (Алина).
* **Глава 1 (Автоворонка прогрева):** 7 сценарных шагов. Автоматическая проверка возраста (18+), сбор аналитики вовлеченности (время набора текста, выбор веток) и подвод к экрану оплаты без участия оператора.
* **Глава 2 (Платный диалог):** Живой чат с актрисой. Баланс расходуется пакетами (микротранзакции). Списание происходит исключительно за ответы героини.
* **Базовый оффер:** 149 ₽ за пакет из 25 сообщений через Систему быстрых платежей (СБП).

## 3. Схема базы данных (PostgreSQL)

### Основные таблицы

* `users`: Аккаунты пользователей, Telegram ID, текущий баланс оплаченных сообщений (`balance_messages`).
* `characters`: Игровые персонажи (ID 1 — «Алина»).
* `actresses`: Профили операторов/актрис со статусами активности (`online`, `offline`).
* `character_sessions`: Сессии прохождения с указанием `current_chapter`, `current_act`, статуса (`active`, `frozen_crisis`, `permanently_closed`) и счетчика монотонной последовательности `msg_seq_counter`.
* `transactions`: Журнал аудита транзакций (`pack_purchase`, `message_burn`). Баланс пользователя не может быть изменен напрямую без строки в этой таблице.
* `messages`: История переписки клиентов и актрисы с привязкой к сессии, типу отправителя (`user`/`actress`) и ID транзакции списания.
* `message_hold_queue`: Очередь сообщений, отправленных на повторную модерацию при задержках или сбоях сети.
* `analytics_events`: Аналитический журнал действий без привязки к PII (связь через хэшированный `analytics_uuid`).
* `blocked_underage_users`: Перманентный реестр блокировки несовершеннолетних по `telegram_id`.

### Механизм защиты баланса (Триггер СУБД)

Целостность финансового ядра обеспечивается на уровне базы данных:

```sql
CREATE OR REPLACE FUNCTION apply_transaction_to_balance()
RETURNS TRIGGER AS $$
DECLARE
    v_current_balance INT;
BEGIN
    SELECT balance_messages INTO v_current_balance
    FROM users WHERE id = NEW.user_id FOR UPDATE;

    IF (v_current_balance + NEW.messages_delta) < 0 THEN
        RAISE EXCEPTION 'Balance integrity violation: balance % cannot be decreased by %',
            v_current_balance, NEW.messages_delta;
    END IF;

    UPDATE users
    SET balance_messages = balance_messages + NEW.messages_delta,
        updated_at = NOW()
    WHERE id = NEW.user_id;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

## 4. Контур безопасности (Safety & Moderation)

1. **Входная валидация:** Все входящие пользовательские реплики (шаг 4 Главы 1 и поток Главы 2) передаются в `handle_incoming_client_message`.
2. **Классификатор:** Обрабатывает текст и скользящее окно истории (последние 4 реплики) через Structured Outputs (`json_schema`, `strict: True`):
   * `underage: true` → немедленная блокировка в `blocked_underage_users`, перевод сессии в `permanently_closed`.
   * `acute_risk: true` → блокировка чата, отправка контактов кризисных линий, статус сессии `frozen_crisis`.
   * `distress: true` → допуск сообщения с флагом `distress_marker = TRUE` для особого внимания актрисы.
3. **Очередь удержания (Hold Queue):** При недоступности внешнего шлюза модерации реплика падает в очередь со статусом `pending`. Фоновый процесс `hold_queue_worker` обрабатывает её по FIFO (`SKIP LOCKED`) с экспоненциальным бэкоффом.
